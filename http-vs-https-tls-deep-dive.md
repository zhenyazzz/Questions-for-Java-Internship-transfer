# HTTP vs HTTPS: что даёт TLS, TCP handshake и TLS handshake

## 1. Главная идея

**HTTP** — данные идут без TLS, то есть по сети их можно прочитать или изменить.

**HTTPS** — это **HTTP внутри TLS**:

```text
HTTP-запрос / HTTP-ответ
        ↓
TLS: шифрование + проверка целостности + проверка сервера
        ↓
TCP-соединение
        ↓
IP-сеть
```

То есть сначала создаётся обычное TCP-соединение, потом поверх него выполняется TLS handshake, и только после этого браузер отправляет HTTP-запрос уже защищённо.

---

## 2. Что конкретно даёт TLS

TLS даёт три главные вещи.

### 2.1. Шифрование

Без TLS данные видны в сети.

С TLS содержимое HTTP скрыто:

- headers;
- cookies;
- access token;
- body запроса;
- body ответа;
- HTML / JSON / файлы.

Наблюдатель может видеть факт соединения, IP-адрес, порт, примерный размер трафика, но не содержимое HTTP.

### 2.2. Целостность

TLS не только шифрует данные, но и защищает их от незаметного изменения.

Если кто-то посередине попробует изменить байты, например подменить JSON-ответ или JavaScript-файл, проверка целостности сломается, и соединение будет считаться повреждённым.

### 2.3. Проверка сервера

TLS позволяет клиенту проверить, что он подключился к настоящему серверу.

Для этого сервер отправляет **сертификат**. Браузер проверяет:

- сертификат выпущен для нужного домена;
- сертификат не просрочен;
- сертификат подписан доверенным центром сертификации;
- цепочка сертификатов корректная;
- сервер владеет приватным ключом от этого сертификата.

Итог: HTTPS защищает от ситуации, когда кто-то между клиентом и сервером пытается притвориться настоящим сайтом.

---

## 3. TCP handshake: зачем он нужен

Перед TLS сначала нужен TCP, потому что TLS работает поверх TCP.

TCP handshake — это установление соединения между клиентом и сервером.

Он состоит из трёх сообщений:

```text
1. Client -> Server: SYN
2. Server -> Client: SYN ACK
3. Client -> Server: ACK
```

После этого TCP-соединение установлено.

Важно: **TCP handshake не шифрует данные** и не проверяет сертификаты. Он только создаёт надёжный транспортный канал, по которому дальше можно гонять байты.

TCP даёт:

- соединение между клиентом и сервером;
- порядок доставки байтов;
- повторную отправку потерянных сегментов;
- контроль доставки;
- поток байтов для верхних протоколов.

Но TCP не даёт:

- шифрование;
- защиту от чтения;
- защиту от подмены на уровне приложения;
- проверку домена;
- сертификаты.

---

## 4. TLS handshake: зачем он нужен

TLS handshake начинается **после TCP handshake**.

Его цель — подготовить защищённый канал.

Во время TLS handshake клиент и сервер должны:

1. договориться о версии TLS и криптографических алгоритмах;
2. проверить сервер через сертификат;
3. безопасно получить общий секрет;
4. из общего секрета создать симметричные ключи;
5. подтвердить, что handshake не был подменён;
6. начать передавать application data, то есть HTTP.

---

## 5. Упрощённая схема как на картинке

Картинка показывает классическую идею: сначала TCP handshake, потом TLS handshake, потом application data.

```text
CLIENT                                            SERVER

SYN                         -------------------->
                            <-------------------- SYN ACK
ACK                         -------------------->

ClientHello                 -------------------->
                            <-------------------- ServerHello
                            <-------------------- Certificate
                            <-------------------- ServerHelloDone

ClientKeyExchange           -------------------->
ChangeCipherSpec            -------------------->
Finished                    -------------------->

                            <-------------------- ChangeCipherSpec
                            <-------------------- Finished

Application Data            -------------------->
                            <-------------------- Application Data
```

![Описание картинки](https://habrastorage.org/r/w1560/files/e52/387/364/e5238736493f41489f5df57f94310962.png)

Смысл по блокам:

1. **SYN / SYN ACK / ACK** — TCP-соединение установлено.
2. **ClientHello** — клиент говорит, какие версии TLS и алгоритмы поддерживает.
3. **ServerHello** — сервер выбирает параметры TLS.
4. **Certificate** — сервер отправляет сертификат, чтобы клиент мог проверить домен и доверие.
5. **ClientKeyExchange** — клиент участвует в создании общего секрета.
6. **ChangeCipherSpec** — сторона говорит: дальше буду использовать согласованные ключи и шифрование.
7. **Finished** — проверка, что handshake прошёл корректно и никто его не подменил.
8. **Application Data** — теперь внутри TLS передаётся обычный HTTP.

---

## 6. Что такое ClientHello

**ClientHello** — первое сообщение TLS handshake от клиента.

В нём клиент отправляет:

- поддерживаемые версии TLS;
- поддерживаемые cipher suites;
- случайное число клиента;
- SNI — имя домена, к которому клиент хочет подключиться;
- ALPN — какой протокол нужен внутри TLS, например HTTP/1.1 или HTTP/2;
- параметры для обмена ключами.

SNI важен, потому что на одном IP может быть много сайтов. Серверу нужно понять, какой сертификат отправлять.

---

## 7. Что такое ServerHello и Certificate

**ServerHello** — ответ сервера.

Сервер выбирает:

- версию TLS;
- cipher suite;
- параметры обмена ключами;
- протокол через ALPN, если нужно.

После этого сервер отправляет **Certificate**.

Сертификат нужен не для того, чтобы напрямую шифровать весь трафик. Он нужен, чтобы связать домен с публичным ключом сервера и доказать, что сервер настоящий.

Браузер проверяет сертификат. Если сертификат плохой, просроченный, не для того домена или не имеет доверенной цепочки, нормальный клиент должен остановить соединение.

---

## 8. Как появляются ключи шифрования

Во время TLS handshake клиент и сервер создают общий секрет.

Важно: они не отправляют готовый общий ключ прямо по сети.

В современных TLS обычно используется Diffie-Hellman-подобный обмен, например ECDHE. Идея такая:

- клиент отправляет свои параметры;
- сервер отправляет свои параметры;
- каждый на своей стороне вычисляет одинаковый общий секрет;
- наблюдатель видит обмен, но не может вычислить итоговый секрет.

Потом из общего секрета создаются симметричные ключи.

Почему симметричные? Потому что ими быстро шифровать большой объём данных: JSON, HTML, файлы, картинки и т.д.

---

## 9. Что такое ChangeCipherSpec и Finished

**ChangeCipherSpec** означает: “дальше я перехожу на согласованные ключи и буду использовать шифрование”.

**Finished** — это контрольное сообщение. Оно подтверждает, что обе стороны видели один и тот же handshake и что его никто не подменил.

После Finished TLS handshake считается завершённым.

Теперь можно отправлять **Application Data**.

Для HTTPS application data — это HTTP-запросы и HTTP-ответы, но уже внутри TLS.

---

## 10. Что такое Application Data

Application Data — это полезные данные приложения.

В случае HTTPS это обычный HTTP:

```http
GET /profile HTTP/1.1
Host: example.com
Cookie: session=abc
```

Но по сети этот запрос уже не летит открытым текстом. Он упакован в TLS records, зашифрован и защищён от изменения.

---

## 11. Коротко по времени и round trips

Если очень грубо:

1. TCP handshake требует один round trip.
2. TLS handshake требует дополнительные round trips.
3. Только потом идёт HTTP application data.

Именно поэтому HTTPS исторически имел больший стартовый overhead, чем HTTP: перед первым HTTP-запросом нужно сделать больше обменов.

Но в современных версиях TLS, особенно TLS 1.3, handshake стал короче, а повторные подключения могут быть быстрее за счёт session resumption.

---

## 12. Главное отличие HTTP и HTTPS в одном примере

### HTTP

```text
Client -> TCP -> Server -> HTTP открытым текстом
```

Проблемы:

- можно прочитать данные;
- можно изменить данные;
- нет нормальной проверки сервера;
- cookies и tokens могут утечь.

### HTTPS

```text
Client -> TCP handshake -> TLS handshake -> HTTP внутри TLS -> Server
```

Что появляется:

- данные шифруются;
- изменение данных обнаруживается;
- сервер проверяется через сертификат;
- после handshake весь HTTP идёт как application data внутри TLS.

---

## 13. Ответ для собеседования

HTTPS — это обычный HTTP, но переданный через TLS. Сначала клиент и сервер устанавливают TCP-соединение через SYN, SYN ACK и ACK. TCP нужен только для транспорта: он не шифрует данные и не проверяет сервер.

После TCP начинается TLS handshake. Клиент отправляет ClientHello со списком поддерживаемых версий TLS, алгоритмов, SNI и параметров обмена ключами. Сервер отвечает ServerHello, выбирает параметры и отправляет сертификат. Клиент проверяет сертификат: домен, срок действия и цепочку доверия. Затем клиент и сервер создают общий секрет, получают симметричные ключи, обмениваются Finished-сообщениями и начинают передавать application data.

Для HTTPS application data — это HTTP-запросы и ответы. TLS даёт шифрование, целостность и проверку сервера. Поэтому в HTTP данные идут открыто, а в HTTPS тот же HTTP идёт внутри защищённого TLS-канала.
