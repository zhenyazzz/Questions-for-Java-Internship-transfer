# HTTP vs HTTPS: TLS, сертификаты, шифрование и handshake

## Коротко: в чём главная разница

**HTTP** — это протокол прикладного уровня для обмена запросами и ответами между клиентом и сервером. Если HTTP используется без TLS, данные передаются **открытым текстом**: URL-путь, заголовки, cookies, тело запроса и тело ответа могут быть прочитаны или изменены тем, кто находится между клиентом и сервером.

**HTTPS** — это не “другой HTTP” и не новый набор HTTP-методов. **HTTPS = HTTP поверх TLS**. Сначала клиент и сервер устанавливают защищённый TLS-канал, а уже внутри этого канала передаются обычные HTTP-сообщения.

Главные свойства HTTPS:

1. **Конфиденциальность** — посторонний наблюдатель не видит содержимое HTTP-запросов и ответов.
2. **Целостность** — если данные изменить по пути, TLS это обнаружит.
3. **Аутентификация сервера** — клиент может проверить, что он подключился именно к нужному сайту, а не к поддельному серверу.

---

## Что видно в HTTP без TLS

При обычном HTTP данные идут по сети в читаемом виде. Если пользователь открывает сайт, отправляет логин, пароль, token, cookie или любую личную информацию, то участник сети между клиентом и сервером потенциально может это увидеть.

Например, при HTTP злоумышленник в той же Wi-Fi сети или промежуточный прокси может увидеть:

- адрес сайта и путь запроса;
- заголовки запроса;
- cookies;
- тело POST-запроса;
- ответ сервера;
- HTML, JSON, картинки и другие данные;
- может попытаться изменить ответ сервера перед тем, как он попадёт к пользователю.

HTTP сам по себе не доказывает, что сервер настоящий. Если пользователь думает, что подключился к `example.com`, обычный HTTP не даёт криптографической гарантии, что ответ пришёл именно от настоящего владельца `example.com`.

---

## Что добавляет HTTPS

HTTPS добавляет между TCP-соединением и HTTP-протоколом слой TLS.

Упрощённо стек выглядит так:

```text
HTTP
TLS
TCP
IP
```

То есть браузер не отправляет HTTP-запрос сразу в TCP-сокет. Сначала он устанавливает TCP-соединение, затем выполняет TLS handshake, договаривается с сервером о параметрах защиты, проверяет сертификат, создаёт общие ключи шифрования, и только после этого отправляет HTTP-запрос уже внутри защищённого канала.

Важно: HTTPS не меняет смысл HTTP как прикладного протокола. Запросы и ответы всё ещё остаются HTTP-запросами и HTTP-ответами. Разница в том, что теперь они передаются внутри зашифрованного и защищённого TLS-соединения.

---

## TLS: что это такое

**TLS** — Transport Layer Security. Это криптографический протокол, который защищает соединение между двумя сторонами: обычно между браузером и сервером.

TLS решает три главные задачи.

### 1. Конфиденциальность

Данные шифруются. Наблюдатель в сети может видеть, что клиент подключился к какому-то IP-адресу и передаёт данные, но не должен видеть содержимое HTTP-запросов и ответов.

Он не должен видеть:

- cookies;
- access tokens;
- пароли;
- JSON-тела запросов;
- HTML-ответы;
- персональные данные;
- содержимое файлов.

### 2. Целостность

TLS защищает данные от незаметного изменения. Если кто-то попробует поменять байты в зашифрованном потоке, проверка целостности не пройдёт, и соединение будет считаться повреждённым.

Это важно не только для паролей. Например, без защиты целостности злоумышленник мог бы изменить JavaScript-файл, HTML-страницу, JSON-ответ или параметры платежа.

### 3. Аутентификация

Клиент проверяет сертификат сервера и убеждается, что сервер имеет право представляться конкретным доменом.

Например, если браузер открывает:

```text
https://bank.example
```

он должен проверить, что сервер предъявил сертификат, действительный именно для `bank.example`, подписанный доверенным центром сертификации и не просроченный.

---

## Почему TLS использует и асимметричное, и симметричное шифрование

В TLS используются разные криптографические механизмы, потому что у них разные задачи.

### Асимметричная криптография

Асимметричная криптография использует пару ключей:

- **private key** — приватный ключ, хранится только у владельца;
- **public key** — публичный ключ, может быть известен всем.

В HTTPS публичный ключ сервера содержится в сертификате, а приватный ключ остаётся на сервере.

Асимметричная криптография нужна для:

- проверки подлинности сервера;
- безопасного согласования ключей;
- цифровых подписей;
- доказательства, что сервер владеет приватным ключом, соответствующим сертификату.

Но асимметричная криптография относительно дорогая и медленная для шифрования больших объёмов данных. Поэтому TLS не шифрует весь HTTP-трафик только RSA или ECDSA.

### Симметричная криптография

Симметричная криптография использует один общий секретный ключ для шифрования и расшифрования данных.

Она намного быстрее и подходит для постоянной передачи трафика:

- HTML;
- JSON;
- картинки;
- файлы;
- API-ответы;
- stream-данные.

Поэтому TLS работает так:

1. Во время handshake клиент и сервер безопасно договариваются об общих секретах.
2. Из этих секретов выводятся симметричные ключи.
3. Основной HTTP-трафик шифруется уже быстрым симметричным шифрованием.

---

## Что такое сертификат

**TLS-сертификат** — это цифровой документ, который связывает доменное имя с публичным ключом.

Сертификат обычно содержит:

- домены, для которых он действителен;
- публичный ключ сервера;
- владельца или организацию, если это применимо;
- срок действия;
- издателя сертификата;
- цифровую подпись издателя;
- дополнительные расширения, например Subject Alternative Name.

Сам по себе сертификат не “шифрует сайт”. Он нужен, чтобы клиент получил публичный ключ сервера и мог проверить, что этот ключ действительно принадлежит нужному домену.

---

## Центры сертификации и цепочка доверия

Браузер не может лично знать публичный ключ каждого сайта в интернете. Поэтому используется модель доверия через **Certificate Authority**, то есть центр сертификации.

Идея такая:

1. В браузере или операционной системе уже есть набор доверенных корневых сертификатов.
2. Сервер показывает свой сертификат.
3. Этот сертификат подписан промежуточным центром сертификации.
4. Промежуточный сертификат связан с корневым сертификатом.
5. Если цепочка подписей корректна и доходит до доверенного корневого сертификата, браузер доверяет сертификату сайта.

Упрощённая цепочка:

```text
Root CA
  -> Intermediate CA
      -> Server certificate for example.com
```

Корневой сертификат обычно не подписывает сайты напрямую. Чаще он подписывает промежуточные сертификаты, а уже промежуточные центры выпускают сертификаты для сайтов.

---

## Что именно проверяет браузер в сертификате

Когда браузер подключается к HTTPS-сайту, он не просто смотрит, что “сертификат есть”. Он выполняет несколько проверок.

### 1. Доменное имя

Сертификат должен быть выдан именно для того домена, к которому подключается пользователь.

Если пользователь открывает:

```text
https://api.example.com
```

то сертификат должен быть действителен для `api.example.com` или подходящего wildcard-домена, например `*.example.com`.

Если сертификат выдан для другого домена, браузер покажет ошибку.

### 2. Срок действия

У сертификата есть дата начала и дата окончания действия. Если сертификат просрочен или ещё не начал действовать, браузер не должен считать соединение доверенным.

### 3. Цепочка доверия

Браузер проверяет, что сертификат сервера подписан доверенной цепочкой, которая заканчивается корневым сертификатом из trust store браузера или операционной системы.

### 4. Цифровая подпись

Браузер проверяет криптографическую подпись сертификата. Это нужно, чтобы убедиться, что сертификат не был подделан или изменён.

### 5. Назначение сертификата

Сертификат должен быть пригоден для использования в TLS-серверной аутентификации. Для этого существуют специальные расширения сертификата.

### 6. Отзыв сертификата

Иногда сертификат нужно отозвать раньше срока: например, если приватный ключ утёк. Для проверки отзыва могут использоваться механизмы вроде CRL и OCSP. На практике браузеры и инфраструктура могут применять разные стратегии проверки отзыва, но сама идея такая: сертификат может стать недоверенным до окончания срока действия.

---

## TLS handshake: что происходит при подключении

TLS handshake — это начальная фаза соединения, во время которой клиент и сервер:

- договариваются о версии TLS;
- выбирают криптографические алгоритмы;
- сервер отправляет сертификат;
- клиент проверяет сертификат;
- стороны создают общие секреты;
- из этих секретов получают ключи для шифрования;
- после этого начинают передавать HTTP-трафик защищённо.

Ниже — упрощённое объяснение современного TLS handshake на примере TLS 1.3.

---

## Упрощённый TLS 1.3 handshake

### Шаг 1. ClientHello

Клиент отправляет серверу сообщение **ClientHello**.

В нём клиент сообщает:

- поддерживаемые версии TLS;
- наборы криптографических алгоритмов;
- случайные данные клиента;
- расширения TLS;
- имя сервера через SNI;
- параметры для обмена ключами, например ECDHE key share;
- какие протоколы прикладного уровня поддерживает, например HTTP/1.1 или HTTP/2 через ALPN.

SNI нужен потому, что на одном IP-адресе может находиться много HTTPS-сайтов. Сервер должен понять, сертификат какого домена ему отправить.

ALPN нужен, чтобы клиент и сервер договорились, какой прикладной протокол использовать внутри TLS: например HTTP/1.1 или HTTP/2.

### Шаг 2. ServerHello

Сервер отвечает **ServerHello**.

Он выбирает:

- версию TLS;
- набор криптографических алгоритмов;
- свои параметры для обмена ключами;
- прикладной протокол, если используется ALPN.

После обмена параметрами клиент и сервер уже могут вычислить общий секрет, не передавая сам секрет по сети напрямую.

### Шаг 3. Сертификат сервера

Сервер отправляет свой сертификат и обычно промежуточные сертификаты, необходимые для построения цепочки доверия.

Клиент проверяет:

- подходит ли сертификат к домену;
- не истёк ли срок действия;
- доверена ли цепочка;
- корректны ли подписи;
- подходит ли сертификат для server authentication.

Если проверка не проходит, браузер останавливает соединение или показывает пользователю предупреждение.

### Шаг 4. Доказательство владения приватным ключом

Сервер должен доказать, что он не просто скопировал чужой сертификат, а действительно владеет приватным ключом, соответствующим публичному ключу в сертификате.

Для этого сервер подписывает часть handshake-данных своим приватным ключом. Клиент проверяет подпись с помощью публичного ключа из сертификата.

Если подпись корректна, клиент понимает: сервер владеет нужным приватным ключом.

### Шаг 5. Получение симметричных ключей

Клиент и сервер независимо вычисляют общий секрет на основе обмена ключами, например через ECDHE.

Затем из этого секрета выводятся рабочие ключи:

- ключи для шифрования данных от клиента к серверу;
- ключи для шифрования данных от сервера к клиенту;
- дополнительные значения для проверки целостности.

Важно: общий секрет не передаётся по сети в готовом виде. Даже если злоумышленник записывает весь handshake, он не должен получить итоговые ключи.

### Шаг 6. Finished

Клиент и сервер отправляют сообщения Finished. Эти сообщения подтверждают, что handshake не был подменён и обе стороны получили одинаковые ключи.

После этого TLS-соединение готово, и внутри него можно передавать HTTP.

---

## Что происходит после handshake

После успешного handshake браузер отправляет HTTP-запрос уже внутри TLS-соединения.

Например, логически это может быть обычный HTTP-запрос:

```http
GET /profile HTTP/1.1
Host: example.com
Cookie: session=...
```

Но в сети он не идёт как читаемый текст. Он разбивается на TLS records, шифруется, снабжается проверкой целостности и только потом передаётся по TCP.

Сервер получает зашифрованные TLS records, расшифровывает их, проверяет целостность и передаёт получившийся HTTP-запрос веб-серверу или приложению.

---

## Что видит наблюдатель при HTTPS

HTTPS скрывает содержимое HTTP, но не делает пользователя полностью невидимым.

Наблюдатель всё ещё может видеть некоторые метаданные:

- IP-адрес сервера;
- факт соединения;
- примерный объём переданных данных;
- время соединения;
- иногда доменное имя через DNS-запрос;
- в классическом TLS — SNI, если он не зашифрован;
- используемый порт, обычно 443.

Но наблюдатель не должен видеть:

- путь URL после домена;
- query parameters;
- HTTP-заголовки;
- cookies;
- тело запроса;
- тело ответа;
- содержимое JSON, HTML, файлов и т.д.

Например, при запросе:

```text
https://example.com/account/orders?userId=123
```

сторонний наблюдатель может понять, что есть соединение с `example.com`, но не должен видеть `/account/orders?userId=123` и содержимое ответа.

---

## Forward secrecy

Современный TLS обычно использует ephemeral Diffie-Hellman, например ECDHE. Это даёт свойство **forward secrecy**.

Смысл: даже если приватный ключ сервера будет украден в будущем, старые записанные TLS-сессии не должны автоматически расшифроваться.

Почему это важно:

1. Злоумышленник может сегодня записывать зашифрованный трафик.
2. Через год он может украсть приватный ключ сервера.
3. Без forward secrecy он мог бы попытаться расшифровать старый трафик.
4. С forward secrecy старые сессионные ключи не выводятся напрямую из долгосрочного приватного ключа, поэтому украденный ключ сервера не должен раскрывать прошлые сессии.

Это одна из причин, почему современные схемы обмена ключами важны.

---

## Почему нельзя просто “зашифровать публичным ключом сервера”

Иногда кажется, что HTTPS мог бы работать проще: клиент берёт публичный ключ из сертификата, шифрует им все данные, а сервер расшифровывает приватным ключом.

На практике так не делают для основного трафика по нескольким причинам:

- асимметричное шифрование медленное;
- оно неудобно для больших потоков данных;
- нужны отдельные ключи для разных направлений передачи;
- нужны механизмы целостности;
- нужна защита самого handshake;
- нужна forward secrecy.

Поэтому публичный и приватный ключи сервера в основном используются для аутентификации и участия в безопасном установлении сессионных ключей, а основной трафик шифруется симметрическими ключами.

---

## Роль приватного ключа сервера

Приватный ключ сервера — критически важный секрет. Он должен храниться только на сервере или в защищённой инфраструктуре, например в HSM или managed certificate service.

Если приватный ключ украден, злоумышленник может попытаться:

- выдать себя за настоящий сервер;
- пройти проверку владения сертификатом;
- атаковать пользователей, если сможет направить их трафик на свой сервер;
- нарушить доверие к домену.

Именно поэтому сертификаты нужно перевыпускать при компрометации ключа, а старый сертификат — отзывать.

---

## Что такое mTLS

Обычный HTTPS чаще всего проверяет только сервер. То есть клиент проверяет сертификат сервера, но сервер не требует сертификат клиента.

**mTLS** — mutual TLS — это режим, где обе стороны предъявляют сертификаты:

- сервер показывает сертификат клиенту;
- клиент показывает сертификат серверу;
- обе стороны проверяют друг друга.

mTLS часто используют:

- во внутреннем service-to-service общении;
- в банковских и enterprise-интеграциях;
- в Kubernetes/service mesh;
- там, где нужно криптографически подтверждать идентичность клиента.

В обычном браузерном интернете mTLS встречается реже, потому что управлять клиентскими сертификатами для массовых пользователей сложно.

---

## Чем HTTPS защищает от man-in-the-middle

Man-in-the-middle — это ситуация, когда злоумышленник находится между клиентом и сервером и пытается читать или менять трафик.

HTTPS мешает такой атаке так:

1. Злоумышленник не может просто прочитать HTTP-трафик, потому что он зашифрован.
2. Злоумышленник не может незаметно изменить данные, потому что TLS проверяет целостность.
3. Злоумышленник не может просто подменить сервер, потому что ему нужен сертификат для нужного домена и соответствующий приватный ключ.
4. Если он покажет самоподписанный или чужой сертификат, браузер должен выдать ошибку.

Но HTTPS не спасает, если пользователь сам установил вредоносный корневой сертификат, корпоративный прокси намеренно установлен как доверенный, устройство заражено malware или приложение отключило проверку сертификатов.

---

## Что HTTPS не решает

HTTPS защищает транспорт между клиентом и сервером, но не делает приложение автоматически безопасным.

HTTPS не исправляет:

- SQL injection;
- XSS;
- CSRF;
- слабые пароли;
- утечки из логов;
- неправильную авторизацию;
- хранение токенов в небезопасном месте;
- уязвимости backend-кода;
- вредоносный JavaScript, который сам сайт отдал пользователю;
- компрометацию сервера.

Если приложение само отправило пользователю вредный скрипт, HTTPS честно и безопасно доставит этот вредный скрипт. TLS защищает канал, но не проверяет бизнес-логику приложения.

---

## HTTP vs HTTPS в одной таблице

| Критерий | HTTP | HTTPS |
|---|---|---|
| Передача данных | Открытый текст | Зашифрованный TLS-канал |
| Конфиденциальность | Нет | Да |
| Защита от изменения данных | Нет встроенной криптографической защиты | Да, изменение обнаруживается |
| Проверка сервера | Нет | Да, через сертификат |
| Типичный порт | 80 | 443 |
| Cookies и токены | Видны в сети | Скрыты внутри TLS |
| Защита от MITM | Практически нет | Да, при правильной проверке сертификатов |
| Использование в production | Нежелательно для реальных данных | Стандарт по умолчанию |

## Простой пример для собеседования

Можно объяснить так:

> HTTP — это способ обмениваться запросами и ответами, но без защиты канала. Данные идут открытым текстом, поэтому их можно прочитать или изменить по пути. HTTPS — это тот же HTTP, но внутри TLS. TLS сначала выполняет handshake: клиент и сервер договариваются об алгоритмах, сервер показывает сертификат, клиент проверяет домен, срок действия и цепочку доверия, после чего стороны получают общие симметричные ключи. Дальше весь HTTP-трафик шифруется, защищается от изменения и передаётся через этот TLS-канал. Сертификат нужен не для того, чтобы “магически шифровать сайт”, а чтобы связать домен с публичным ключом и подтвердить подлинность сервера.

---

## Более глубокий ответ для middle-level собеседования

HTTPS — это HTTP over TLS. Сначала устанавливается TCP-соединение, потом выполняется TLS handshake. В handshake клиент отправляет ClientHello со списком поддерживаемых версий TLS, cipher suites, SNI, ALPN и параметрами обмена ключами. Сервер отвечает ServerHello, выбирает параметры, отправляет сертификат и доказывает владение приватным ключом. Клиент проверяет, что сертификат подходит к домену, не просрочен, подписан доверенной цепочкой и предназначен для server authentication.

После этого клиент и сервер через механизм обмена ключами, обычно ECDHE, получают общий секрет и на его основе создают симметричные ключи для шифрования трафика. Основные данные не шифруются напрямую публичным ключом сервера, потому что это медленно и не даёт нормальных свойств для потоковой передачи. Публичный и приватный ключи нужны прежде всего для аутентификации и защиты handshake, а трафик после handshake шифруется быстрым симметричным шифрованием.

В результате HTTPS даёт конфиденциальность, целостность и аутентификацию сервера. Наблюдатель может видеть факт соединения, IP, примерный объём трафика и некоторые метаданные, но не должен видеть HTTP headers, cookies, тело запроса, тело ответа и путь URL. При этом HTTPS не заменяет безопасность приложения: он не защищает от XSS, SQL injection, ошибок авторизации или компрометации сервера.

## Частые ошибки в понимании

### Ошибка 1. “HTTPS — это отдельный протокол вместо HTTP”

Правильнее: HTTPS — это HTTP, передаваемый через TLS.

### Ошибка 2. “Сертификат нужен для шифрования всех данных”

Сертификат содержит публичный ключ и подтверждает принадлежность ключа домену. Основной трафик после handshake обычно шифруется симметрическими сессионными ключами.

### Ошибка 3. “Если сайт на HTTPS, значит он безопасный”

HTTPS говорит, что канал до сайта защищён и сертификат прошёл проверку. Но сам сайт всё равно может быть фишинговым, взломанным или иметь уязвимости.

### Ошибка 4. “TLS скрывает вообще всё”

TLS скрывает содержимое HTTP, но часть сетевых метаданных может оставаться видимой: IP-адрес, объём трафика, время соединения, DNS-запросы, иногда SNI.

### Ошибка 5. “Можно отключить проверку сертификата, если мешает”

Отключение проверки сертификата разрушает одну из ключевых гарантий HTTPS — аутентификацию сервера. После этого соединение может быть зашифрованным, но клиент уже не знает, с кем именно он говорит.

## Итог

Разница между HTTP и HTTPS не в методах, статусах или формате запросов. Разница в наличии защищённого TLS-слоя.

HTTP без TLS передаёт данные открыто и не даёт криптографической гарантии, что сервер настоящий и данные не изменили по пути.

HTTPS добавляет TLS, а TLS даёт:

- шифрование;
- защиту целостности;
- проверку подлинности сервера через сертификаты;
- безопасное согласование сессионных ключей;
- защиту от большинства классических man-in-the-middle атак при правильной проверке сертификатов.

Если нужно запомнить одной фразой:

> HTTPS — это обычный HTTP, но переданный через TLS-канал, который сначала проверяет сервер по сертификату, затем создаёт общие симметричные ключи и дальше шифрует и защищает весь HTTP-трафик.
