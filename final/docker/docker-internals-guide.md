# Базовая формулировка: что такое Docker под капотом

### Короткая формулировка

**Docker — это система упаковки и запуска Linux-процессов.**

Контейнер не является отдельной виртуальной машиной и не запускает отдельное ядро. Контейнер — это обычный процесс Linux, который запускается с ограничениями и изоляцией на уровне ядра.

### Три механизма ядра

- **Namespaces** — определяют, что процесс _видит_ (свой PID, сеть, mount, hostname и т.д.).
- **cgroups** — определяют, что процесс _может потреблять_ (CPU, память, I/O).
- **OverlayFS** (реализация Union FS) — «склеивает» несколько слоёв в одну корневую ФС, которую процесс _читает и изменяет_.

### Что из этого следует

Docker решает две разные задачи:

1. **Сборка** — из `Dockerfile` получается **image** (неизменяемый шаблон файловой системы + метаданные).
2. **Запуск** — из image создаётся **container** (изолированный процесс с собственным writable-слоем поверх read-only слоёв образа).

Дальше материал идёт в том же порядке, в котором это обычно объясняют на собеседовании: сначала рецепт (`Dockerfile`), потом физика слоёв, потом образ, потом контейнер.

# Dockerfile

### Что такое Dockerfile

**Dockerfile** — это текстовый рецепт сборки образа: последовательность инструкций, которые `docker build` выполняет по шагам.

Каждый шаг сборки:

- читает результат предыдущих шагов (текущий промежуточный rootfs);
- применяет одну инструкцию;
- при необходимости фиксирует новое состояние как **слой**;
- в конце получается финальный **image**.

Dockerfile описывает _как собрать_ образ. Он не описывает runtime-поведение контейнера так же полно, как сам запущенный процесс: часть поведения задаётся метаданными образа (`CMD`, `ENTRYPOINT`, `ENV`), часть — параметрами `docker run` / orchestrator.

### Инструкции, которые создают файловые слои

Обычно **новый файловый слой** в образе создают инструкции, которые реально меняют файлы в rootfs:

- `RUN` — выполняет команду внутри промежуточного контейнера сборки (установка пакетов, `mvn package`, создание каталогов).
- `COPY` — копирует файлы с хоста сборки в образ.
- `ADD` — то же, что `COPY`, плюс поддержка URL и распаковки tar (на практике чаще предпочитают явный `COPY`).

Причина простая: после такого шага на диске появляется **дельта файловой системы** — новый immutable-слой.

### Инструкции, которые в основном меняют метаданные образа

Инструкции `ENV`, `WORKDIR`, `CMD`, `ENTRYPOINT`, `EXPOSE`, `LABEL`, `USER`, `ARG` в основном обновляют JSON-конфигурацию образа (`config.Env`, `config.WorkingDir`, `config.Cmd` и т.д.).

Они отражаются в **history** образа, но обычно **не добавляют** новый `diff/`-слой с файловыми изменениями.

### Образ как манифест

Готовый **image** — это не «одна большая папка с файлами». По сути это **манифест** (JSON): _«Я состою из слоя A, слоя B и слоя C, а запускать меня нужно командой X»_.

Физически на диске лежат:

- несколько **папок-слоёв** (каждая с digest `sha256:...`);
- **маленький JSON** (config + ссылки на слои + `Cmd` / `Entrypoint` / `Env`);
- опционально **тег** (`my-app:latest`) — удобное имя для человека.

Подробнее про manifest в registry — в главе [Image](#image-образ); ниже — **как этот манифест рождается** при сборке.

### Как работает `docker build`: временные контейнеры

Сборка образа — это не «магическое копирование папок». Инженерный трюк Docker: **`docker build` по сути поочерёдно запускает временные контейнеры**.

Движок сборки (классический builder или **BuildKit**) выполняет **каждую строку Dockerfile строго по порядку**. Слои immutable — значит, чтобы выполнить `RUN`, нужен **живой rootfs**, а не правка готовой папки на месте.

Пример:

```dockerfile
FROM ubuntu:24.04
RUN apt-get update && apt-get install -y python3
COPY ./app.py /app/
```

#### Шаг 1: базовый слой (`FROM`)

Docker читает `FROM ubuntu:24.04`, **скачивает** (или берёт локально) уже готовые слои Ubuntu. Это **фундамент** — **Слой №1**. Отдельный временный контейнер на этом шаге обычно не нужен: база уже собрана и лежит как image.

#### Шаг 2: слой через временный контейнер (`RUN`)

Нужно выполнить `RUN apt-get update...`, но **готовый слой менять нельзя**. Что делает Docker:

1. Берёт **Слой №1** и на его основе запускает **временный скрытый контейнер** (intermediate container).
2. Внутри выполняется команда — ФС контейнера меняется (появляются файлы Python).
3. После успешного завершения контейнер **останавливается**.
4. Docker делает **snapshot** только **дельты** изменений относительно входного состояния.
5. Дельта сохраняется как **Слой №2** (новая папка `diff/` на диске). **Временный контейнер удаляется.**

Слой №1 при этом **не тронут**.

#### Шаг 3: следующий слой (`COPY`)

1. Docker «склеивает» для сборки состояние **Слой №1 + Слой №2** и снова поднимает **временный контейнер**.
2. Копирует `app.py` в `/app/`.
3. Фиксирует изменения как **Слой №3**. Временный контейнер снова удаляется.

Каждый `RUN` / `COPY` / `ADD`, создающий файловую дельту, повторяет этот цикл: **контейнер → изменение → commit слоя → удалить контейнер**.

### Финал сборки: рождение манифеста

Когда все строки Dockerfile выполнены, Docker собирает **манифест образа**:

> **Манифест образа (упрощённо):**
>
> - Слой 1: `sha256:7a3d...` (Ubuntu)
> - Слой 2: `sha256:8b4f...` (Python)
> - Слой 3: `sha256:9c5a...` (твой код)
> - Config: запускать `python3 /app/app.py`, `WORKDIR`, `ENV`, …

Манифесту присваивают **тег**, например `my-app:latest` (или оставляют только digest).

**Итог на диске:** N папок со слоями + JSON, который их связывает. Образ собран.

### Почему кэш сборки работает так просто

Повторный `docker build` после изменения только `app.py`:

1. Docker сравнивает шаги с **предыдущей сборкой** (digest слоёв + контекст инструкций).
2. Шаги 1 и 2 (`FROM`, `RUN apt-get...`) **не изменились** → временные контейнеры для них **не запускаются**, берутся готовые **Слой 1** и **Слой 2** из кэша.
3. Временный контейнер выполняется **только для шага 3** (`COPY`), потому что изменился вход (файл `app.py` или его checksum).

Это и есть **Docker layer cache** (BuildKit кэширует ещё агрессивнее, в том числе между сборками и в remote cache).

### Практический вывод для Dockerfile

Порядок строк важен именно из-за этой механики:

- всё **стабильное** (базовый образ, `apt install`, `mvn dependency:go-offline`) — **выше**;
- всё **часто меняющееся** (`COPY` исходников) — **ниже**.

Иначе одна правка в `app.py` инвалидирует кэш и заставляет заново гонять тяжёлые `RUN` выше по файлу.

# Docker Layers (слои)

### Что такое слой

Слой (Layer) — это неизменяемый (read-only) набор изменений в файловой системе. Каждый слой представляет собой разницу (дифференциал) по сравнению с предыдущим слоем. Это можно представить как «снимок» (snapshot) конкретного шага: добавили пакет, скопировали код, создали папку.

Слой = дельта rootfs: какие файлы добавлены, изменены или (в метаданных слоя) помечены на удаление при сборке.

При сборке (`docker build`) каждая инструкция `RUN` / `COPY` / `ADD` может добавить **ещё один** read-only слой в будущий **image**. В итоге образ — это **пирог** из нескольких таких неизменяемых пластов, сложенных снизу вверх.

### Пирог слоёв при запуске контейнера

Когда ты запускаешь контейнер (`docker run`), Docker **не копирует** весь образ целиком. Он берёт уже готовый **пирог из неизменяемых слоёв image** (все они **Read-Only**) и **нахлобучивает сверху** самый верхний, **тонкий**, доступный для записи слой — **Container Layer** / **Writable Layer**.

```
┌─────────────────────────────────────┐
│  Container Layer (Writable)         │  ← пишем сюда: логи, tmp, изменения
├─────────────────────────────────────┤
│  Слой image N (Read-Only)           │
├─────────────────────────────────────┤
│  …                                  │
├─────────────────────────────────────┤
│  Слой image 1 / base (Read-Only)    │  ← пирог из docker pull / docker build
└─────────────────────────────────────┘
         ↓ OverlayFS склеивает в одну ФС (Merged View = /)
```

Что важно запомнить:

- **Нижняя часть пирога** — только слои **image**. Их несколько, все **immutable**, общие для всех контейнеров с этого образа.
- **Верхняя «шапка»** — **один** слой на **конкретный** контейнер. Только он **writable**; в OverlayFS это **UpperDir**, в терминах Docker — **container layer**.
- Процесс внутри контейнера видит не отдельные пласты, а **единый `/`** — результат наложения всей стопки (UFS / OverlayFS).

Без верхнего writable-слоя контейнер мог бы только **читать** файлы образа, но не создавать и не менять их в rootfs. Именно поэтому «слой» при разговоре о runtime — это всегда **два уровня**: стопка image + container layer сверху.

### Где слои лежат физически

На Linux-хосте с драйвером хранения `overlay2` данные слоёв обычно находятся в:

- **`/var/lib/docker/overlay2/`**

Основные элементы:

- `diff/` — файлы, добавленные или изменённые в этом слое.
- `lower` — ссылка на цепочку нижележащих (родительских) read-only слоёв.
- `merged/` — объединённый вид ФС для запущенного контейнера.
- `work/` — служебная рабочая директория OverlayFS.

**Ключевая мысль:** слой — это реальные байты на диске, адресуемые по digest, а не только строка в `docker history`.

### Неизменяемость слоёв (immutability)

Слои адресуются по содержимому через digest (`sha256:...`).

Если содержимое слоя изменилось хотя бы на один байт, digest станет другим — это уже **новый** слой, а не правка старого «на месте».

Что это даёт:

1. Детерминированный кэш сборки (`docker build`).
2. Безопасную дедупликацию: один и тот же слой хранится один раз.
3. Проверяемую целостность при pull/push.
4. Повторяемость сборок на разных машинах.

Практический сценарий: 100 Java-сервисов на одном базовом образе — общие нижние слои лежат на диске один раз; у каждого сервиса свои верхние слои с артефактом; у каждого **контейнера** — ещё один writable-слой сверху при запуске.

### Union File System и OverlayFS

**Обычная файловая система** (ext4, NTFS на диске) — «плоская» папка: положил `config.txt` в каталог — там может быть **только одна** его версия. Перезаписал файл — старая версия на этом же месте исчезла.

**Union File System (UFS)** — технология, которая берёт **несколько каталогов (слоёв)**, виртуально **накладывает** их друг на друга и показывает приложению **одну общую** файловую систему.

**OverlayFS** — современная и самая распространённая **реализация UFS в Linux**; Docker на Linux по умолчанию использует её через storage driver **`overlay2`**.

Аналогия для собеседования: **стопка прозрачных плёнок** с «рисунками». Каждый слой Docker-образа — одна плёнка. Смотришь сверху вниз — видишь **единую картинку**. В Docker это **Merged View** (`merged/` / `MergedDir`) — именно её процесс внутри контейнера воспринимает как `/`.

Важно не путать термины:

| Термин      | Что это                                         |
| ----------- | ----------------------------------------------- |
| UFS         | идея: несколько слоёв → одно виртуальное дерево |
| OverlayFS   | конкретный драйвер ядра Linux                   |
| `overlay2`  | то, как Docker хранит и монтирует слои на хосте |
| Merged View | то, что видит приложение в контейнере           |

### OverlayFS: как ядро «склеивает» слои

Технически OverlayFS монтирует несколько директорий в один mount view — **Merged View** — то, что процесс внутри контейнера видит как `/`.

Сущности:

- **LowerDir** — стек read-only слоёв образа (снизу вверх).
- **UpperDir** — writable-слой конкретного контейнера (верхний, «для записи»).
- **WorkDir** — служебная рабочая область OverlayFS (нужна ядру для copy-up).
- **MergedDir** — итоговое дерево: результат «склейки» upper + lower.

Когда приложение в контейнере обращается к файлу, оно работает с `MergedDir`. Решение, откуда взять файл или куда писать, принимает **не Docker как отдельная программа**, а **ядро Linux через OverlayFS** — на лету, в момент системного вызова (`open`, `read`, `write`, `unlink`).

### Copy-on-Write (копирование при записи)

**Copy-on-Write (CoW)** — механизм, при котором данные **не копируются заранее**. Копия создаётся **только в момент первой записи** в файл, который до этого существовал только в read-only нижнем слое.

Зачем это Docker: один и тот же image могут использовать сотни контейнеров. Если бы при каждом `docker run` копировался весь rootfs образа, диск и время старта взорвались бы. CoW даёт общие read-only слои + тонкий writable-слой на контейнер.

Три сценария, которые стоит уметь проговорить на собеседовании:

#### Сценарий A: чтение файла (Read)

Контейнер хочет прочитать, например, `/etc/nginx/nginx.conf`.

1. OverlayFS ищет путь в **UpperDir** (writable-слой контейнера).
2. Если файла там нет — спускается по **LowerDir** (слои образа) сверху вниз.
3. Находит файл в read-only слое и отдаёт его процессу.

Копирования нет: чтение идёт напрямую из нижнего слоя. Это быстро и не расходует место в upper layer.

#### Сценарий B: изменение существующего файла (Write / Modify)

Контейнер хочет изменить тот же `/etc/nginx/nginx.conf`, но файл лежит в **нижнем read-only слое** — туда писать нельзя.

1. При попытке записи срабатывает **copy-up** (частный случай CoW): ядро **копирует** `nginx.conf` из lower в **UpperDir**.
2. Запись применяется уже к **копии** на верхнем слое.
3. В `MergedDir` upper «перекрывает» lower — контейнер видит только изменённую версию.

Исходный файл в **image остаётся нетронутым**. Другой контейнер с того же образа по-прежнему видит оригинальный `nginx.conf`.

Аналогия: непрозрачная заплатка на прозрачной плёнке — нижние слои как были, сверху своя версия файла.

#### Сценарий C: удаление файла (Delete)

Контейнер хочет удалить файл, который пришёл из образа. Физически стереть его из read-only слоя нельзя.

1. В **UpperDir** создаётся специальная метка **whiteout** (часто файл вида `.wh.<имя>` в представлении слоя).
2. Для `MergedDir` эта метка **скрывает** файл из нижних слоёв.
3. Для процесса в контейнере файл «удалён»; на диске в слое **образа** он по-прежнему лежит.

После `docker rm` upper layer с whiteout исчезает — при новом контейнере с того же image файл снова виден.

#### Сводка CoW

| Операция               | Где ищем / что делаем             | Меняется image? |
| ---------------------- | --------------------------------- | --------------- |
| Read                   | Upper → lower, без копии          | Нет             |
| Write в файл из образа | copy-up в UpperDir, пишем в копию | Нет             |
| Delete файла из образа | whiteout в UpperDir               | Нет             |
| Create новый файл      | сразу в UpperDir                  | Нет             |

**На собеседовании:** CoW — это не «Docker копирует весь образ при старте», а **ленивое копирование при первой записи** + **whiteout вместо физического delete** из immutable-слоёв.

# Image (образ)

### Что такое image

**Image** — локально разрешённый артефакт: **манифест (JSON)** + **упорядоченный стек immutable read-only слоёв** + ссылки по tag/digest.

Образ — это **шаблон**, а не выполняющийся процесс. Сам по себе image «не бежит».

Состав:

- **манифест / image config** — JSON: список digest слоёв + `Env`, `Cmd`, `Entrypoint`, `WorkingDir`, `User`, … (_«состою из слоёв A, B, C; запускать командой X»_);
- **layer blobs** — физические папки-дельты на диске (`/var/lib/docker/overlay2/`), каждая по `sha256:...`;
- опционально **тег** (`myapp:1.2`) — алиас на digest манифеста.

Как манифест появляется при `docker build` (временные контейнеры, snapshot слоёв) — см. главу [Dockerfile](#dockerfile).

### Почему слои образа только read-only

Когда ты делаешь `docker pull postgres:17`, на диск попадает образ из **нескольких готовых слоёв**. Все они смонтированы и зафиксированы в режиме **Read-Only** — это слои **image**, не контейнера.

Зачем так сделано:

**1. Экономия места на диске**

Запустишь 10 контейнеров Postgres — Docker **не копирует** файлы образа 10 раз. Все 10 экземпляров **одновременно читают одни и те же** read-only слои на хосте. Меняется только тонкий writable-слой у каждого контейнера (логи, данные в `/var/lib/postgresql/data`, если не вынесены в volume).

**2. Безопасность и стабильность шаблона**

Контейнер **физически не может испортить** базовый image. Что бы ни произошло внутри запущенного процесса — сломанный конфиг, удалённые бинарники в merged view — **сами слои образа на хосте остаются неизменными**. Новый контейнер с того же `postgres:17` стартует с чистого шаблона.

Read-only слои образа = **LowerDir** в OverlayFS. Запись в них невозможна; CoW и whiteout работают только через верхний слой (см. ниже в главе про контейнер).

### Manifest в реестре

**Manifest** — JSON-дескриптор в registry (Docker Hub, ECR, Harbor), который связывает:

- digest конфигурации образа;
- упорядоченный список digest-ов layer blob;
- media type, size и прочие метаданные.

При `docker pull` клиент скачивает manifest, затем по digest подтягивает config и слои. Локально из этого собирается **image**.

### Image vs Dockerfile

|              | Dockerfile          | Image                                    |
| ------------ | ------------------- | ---------------------------------------- |
| Форма        | текстовый рецепт    | бинарный/распакованный артефакт на диске |
| Изменяемость | редактируется в git | immutable слои после сборки              |
| Назначение   | описать сборку      | шаблон для запуска контейнеров           |

Один Dockerfile → один собранный image (при фиксированных входах и отсутствии cache bust даёт воспроизводимый digest).

# Container (контейнер)

### Что такое container

**Container** — **runtime-состояние**: изолированный процесс (или группа процессов) + namespaces + cgroups + merged rootfs из OverlayFS + **собственный writable upper layer**.

Коротко:

- **Image** = неизменяемый шаблон (read-only слои).
- **Container** = запущенный экземпляр шаблона + изоляция + свой слой записи.

### Writable layer (container layer)

Image даёт только **read-only** плёнки в стопке. Но контейнеру нужно писать: логи, pid-файлы, временные файлы, изменения конфигов, данные приложения.

Для этого **поверх** всех слоёв образа Docker накладывает **один тонкий Writable Layer** — в терминах OverlayFS это **UpperDir**, его же часто называют **container layer**.

| Слой                       | Режим     | Кто делится между контейнерами    |
| -------------------------- | --------- | --------------------------------- |
| Слои image                 | Read-Only | Да, все контейнеры с одного image |
| Container layer (UpperDir) | Writable  | Нет, у каждого контейнера свой    |

Все изменения ФС во время жизни контейнера (без отдельного volume) идут **только** в этот upper layer. Image и другие контейнеры не затрагиваются — это прямое следствие CoW и immutability нижних слоёв.

После `docker rm` container layer обычно удаляется; при следующем `docker run` writable-слой создаётся заново, read-only стек образа тот же.

### Что происходит при `docker run`

1. Docker (containerd/runc) берёт слои **image** как `LowerDir` (read-only стопка UFS).
2. Создаёт для этого экземпляра **UpperDir** — **writable / container layer**.
3. Монтирует **MergedDir** — процесс видит единый `/`.
4. Создаёт namespaces (PID, net, mount, UTS, IPC, user).
5. Подключает cgroups (лимиты CPU/RAM и т.д.).
6. Запускает процесс с `ENTRYPOINT`/`CMD` из конфига образа (с учётом override в `docker run`).

Несколько контейнеров с одного image **делят** read-only слои и **не делят** upper layer — изменения одного контейнера не портят другой и не меняют image.

### Жизненный цикл и изменения

Пока контейнер работает, все записи в ФС идут в его `UpperDir`. После `docker rm` writable-слой обычно удаляется; image остаётся.

Пересборка image (`docker build`) не трогает уже запущенные контейнеры старого образа — нужен новый deploy с новым image.

### Типичные ошибки в формулировках на собеседовании

- «Контейнер = мини-ВМ» — неверно: одно ядро хоста, общий kernel.
- «Image меняется при работе контейнера» — неверно: меняется только upper layer контейнера.
- «Слой Dockerfile = просто строка в history» — неполно: слой — это digest + `diff/` на диске.

# Краткий ответ на собеседование

1. **Docker** упаковывает и запускает Linux-процессы через namespaces, cgroups и OverlayFS.
2. **Dockerfile** — рецепт; сборка = цепочка **временных контейнеров** → snapshot слоёв → JSON-манифест.
3. **UFS / OverlayFS** — несколько каталогов-слоёв → одна Merged View; Docker использует `overlay2`.
4. Слой — это просто изолированная папка, в которой лежат только те файлы, которые были созданы или изменены на конкретном шаге.

5. Образ (Image) — это текстовый файл-манифест (список), в котором написано: "Так, для этого образа возьми папку-слой А, сверху наложи папку-слой Б, а сверху папку-слой В".

6. Контейнер — это запущенный процесс, для которого Docker взял этот список папок (А, Б, В), виртуально склеил их в одну («наложил» друг на друга) и сказал процессу: "Вот твоя корневая папка, работай".
7. **CoW:** read — из lower; write — copy-up в upper; delete — whiteout; image не портится.
